## What This Project Is

**reNgine** (v2.2.0) is an automated web application reconnaissance and vulnerability scanning suite. It orchestrates security tools (subfinder, nuclei, naabu, ffuf, httpx, etc.) via Celery tasks, stores all results in PostgreSQL, and exposes them through a Django web interface and REST API.

## Common Commands

All operations go through Docker Compose via `make`:

```bash
make setup          # Generate SSL certificates (first-time only)
make up             # Build and start all services
make build          # Build Docker images
make migrate        # Apply database migrations
make username       # Create Django superuser
make down           # Stop and remove containers
make restart        # Restart services
make logs           # Tail logs from all services
make test           # Run test suite
make prune          # Remove containers and volumes (destructive)
```

**Running tests directly:**
```bash
docker-compose exec celery python3 -m unittest tests/test_scan.py
docker-compose exec celery python3 -m unittest tests/test_nmap.py
```

**Running a single Django management command:**
```bash
docker-compose exec web python3 manage.py <command>
```

**Development compose file** (`docker-compose.dev.yml`) can be used alongside the main file for development overrides.

## Architecture

### Service Stack
- **web** – Django 3.2 app (port 8000 internally, exposed via proxy)
- **celery** – Celery worker executing all scan tasks
- **celery-beat** – Scheduler for periodic/continuous scans
- **db** – PostgreSQL 12.3
- **redis** – Message broker and result backend for Celery
- **proxy** – Nginx with SSL termination (port 443)
- **ollama** – Local LLM server (port 11434)

### Django Apps
| App | Responsibility |
|-----|----------------|
| `dashboard` | Projects, notifications, API key settings |
| `targetApp` | Domain targets, WHOIS/DNS data, organizations |
| `scanEngine` | Engine types (YAML configs), wordlists, notification rules |
| `startScan` | Scan history, subdomains, endpoints, vulnerabilities |
| `recon_note` | Reconnaissance notes |
| `api` | REST API endpoints (Django REST Framework) |

### Scan Pipeline (the core logic)

All scan orchestration lives in `web/reNgine/tasks.py` (~4700 lines). The main entry point is `initiate_scan()`, which chains Celery tasks:

1. `subdomain_discovery()` – subfinder, ctfr, sublist3r, tlsx, netlas, chaos
2. `http_crawl()` – httpx probing of discovered subdomains
3. `port_scan()` – naabu + optional nmap
4. `osint()` – email harvesting, employee discovery, Google dorks
5. `fetch_url()` – gospider, hakrawler, waybackurls, katana, gau
6. `dir_file_fuzz()` – ffuf directory/file fuzzing
7. `vulnerability_scan()` – nuclei, dalfox, crlfuzz, s3scanner
8. `waf_detection()` – wafw00f
9. `screenshot()` – Selenium-based screenshots

Scan behavior is controlled entirely by YAML-based engine configurations stored in the `EngineType` model. See `default_yaml_config.yaml` and `web/fixtures/default_scan_engines.yaml` for reference.

### Key Files
- `web/reNgine/tasks.py` – All Celery scan tasks
- `web/reNgine/common_func.py` – Shared utilities (~1700 lines)
- `web/reNgine/definitions.py` – Constants, default values, tool paths
- `web/api/views.py` – REST API (~99k lines, heavily autogenerated via DRF)
- `web/reNgine/llm.py` – OpenAI/Ollama LLM integration for report generation
- `web/reNgine/roles.py` – Role-based permissions (Sys Admin, Pentester, Auditor)

### Data Flow
Targets → Domains → Scans → Subdomains → {IpAddresses, Ports, Endpoints, Vulnerabilities, Emails, Employees, S3Buckets, Dorks}

All scan results are stored relationally in PostgreSQL. Subscans allow focused rescans on specific subdomains or findings.

## Role System

Three roles with progressively restricted permissions:
- **Sys Admin** – Full access including user/system management
- **Penetration Tester** – Initiate scans, modify targets and results
- **Auditor** – Read-only; download reports only

Permissions are defined in `web/reNgine/roles.py` and enforced via `django-role-permissions`.

## Environment Configuration

Key `.env` variables (see `.env` for current values):
- `POSTGRES_*` – Database credentials
- `MAX_CONCURRENCY` / `MIN_CONCURRENCY` – Celery autoscaling (default 80/10)
- `DJANGO_SUPERUSER_*` – Used by non-interactive setup
- `DOMAIN_NAME` – Used for SSL certificate generation

## Fixtures & Default Data

On first run, `entrypoint.sh` loads:
- `web/fixtures/default_scan_engines.yaml` – Predefined scan engine configurations
- `web/fixtures/default_keywords.yaml` – Keywords for "interesting" subdomain flagging
- `web/fixtures/external_tools.yaml` – Registry of installed external tools

## Celery Task Queues

- `initiate_scan_queue` – Scan initialization tasks
- Default queue – All other tasks

Tasks track state in Redis; results are stored in the database via model saves within task functions.
